# RFC-0046 Object storage extension

**Status:** implemented

**Owner:** unassigned

**Depends on:** RFC-0002 (implemented), RFC-0059 (platform CA), RFC-0060 (storage classes)

**Creation date:** 2026-09-22

**Last update:** 2026-09-25 (implemented with Garage; MinIO's public images are gone)

## Summary

An `object-storage` extension giving the platform an S3-compatible bucket store with a
credential per consumer: Garage in the cluster on every profile, buckets declared as
`ObjectBucket` resources by the extensions that need them (Postgres backups, platform
backups, Loki). The provider's object storage (S3, OCI Object Storage)
is the offsite tier: where data must survive the cluster, RFC-0037 writes there directly,
and MinIO replication to it is the follow-up.

## Motivation

Three RFCs need durable object storage; each configuring its own would triple the work
and the credentials.

### Goals

- `shpyrd extensions enable object-storage` and consumers get a bucket and a credential
  that opens only that bucket.
- The same client model on kind, OKE and EKS; nothing in a project namespace can reach
  another project's data.

### Non-Goals

- Exposing buckets to applications as a resource (a later resource type).
- Replacing the provider's object storage for archives; MinIO here is the platform's
  working store, on the profile's block storage class.

## Proposal

- **One store, every profile.** Garage (garagehq.deuxfleurs.fr, single node) in
  `shpyrd-system` on a volume of the profile's class (`SHPYRD_OBJECT_STORAGE_SIZE`: 20Gi
  local and AWS, 50Gi on OCI, the block volume minimum), reached at
  `http://object-storage.shpyrd-system.svc:3900`; its RPC secret, admin token and metrics
  token are generated by a hook into Secret `object-storage-admin`, which only the platform
  reads. Plain HTTP inside the cluster: keys open one bucket each and namespaces are
  isolated by network policy; Garage terminates no TLS itself, a sidecar can when a
  profile needs it.
- **`ObjectBucket`** (`shpyrd.io/v1alpha1`, namespaced): a consumer declares
  `spec: {retentionDays?, deletionPolicy?}` in its namespace; the extension's controller
  creates the bucket `shpyrd-<namespace>-<name>`, a key allowed to read and write that
  bucket and nothing else, and writes Secret `<name>-object-storage` next to it
  (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL`, `BUCKET`, `AWS_REGION`,
  plus `accessKeyId` / `secretAccessKey` for consumers that name keys, such as
  CloudNativePG). Status carries the endpoint, bucket, usage and phase. Deleting the
  resource deletes the key and, with `deletionPolicy: Delete` (the default), the bucket
  and its objects; `Retain` leaves them. Garage has no object versioning; `versioning` is
  accepted for the day it does.
- **Cluster page and CLI.** An Object storage card (capacity of the volume, buckets with
  size and object count) and `shpyrd object-storage buckets`.
- **Why not the provider's service as the store?** S3 or OCI Object Storage can only hand
  out credentials scoped per consumer through cloud IAM (one IAM user or Pod Identity
  association per project, created by the platform with cloud SDKs and IAM rights). Until
  that exists, a shared provider key in project namespaces would open every project's
  backups to any project member who can exec into a database pod. MinIO scopes users
  natively, so the isolation holds on day one on every profile.
- **The offsite tier.** RFC-0037 (platform backups) writes to the provider's bucket
  directly with its own credential, from the platform namespace only, because its purpose
  is to survive the cluster. MinIO bucket replication to that bucket (one credential, held
  by MinIO) is the natural next step for the other consumers and is tracked as a
  follow-up.

### Alternatives

- **The provider's object storage as the store** (the first draft's goal). Deferred for
  the credential reason above; the data path is one flag away once per-consumer cloud
  credentials exist.
- **A bucket per cluster with prefixes per consumer.** Same credential problem, harder
  usage accounting.
- **MinIO** (the plan until implementation day). Its public images were withdrawn from
  quay.io and Docker Hub in 2025, including pinned tags; a platform cannot depend on
  that. Garage has the same properties for this use (S3 API, per-key bucket permissions,
  admin API, usage, lifecycle), a tenth of the footprint, and images that stay.
- **SeaweedFS.** Capable, but its S3 identities are configured through the filer rather
  than an admin API with bucket-scoped keys.

## Design Details

- Manifests (`deploy/components/object-storage`): ConfigMap `garage.toml`
  (`replication_factor = 1`, lmdb, metadata snapshots every 6 h, S3 region `garage`),
  PVC, Service (3900 S3, 3903 admin), Deployment (`dxflrs/garage:v2.4.1`, non-root, TCP
  probes: `/health` answers 503 until the layout exists, which the platform applies
  through this very Service).
- Controller (`internal/controller/objectbucket_controller.go`) with the admin client
  (`pkg/objectstore`): on first use it applies the layout (the node's role, zone `shpyrd`,
  capacity of the volume); per resource `CreateBucket` (global alias), `CreateKey` /
  `ImportKey` (so a credential in a Secret stays stable when the store loses it),
  `AllowBucketKey` read+write; retention through `PutBucketLifecycle` with a
  platform-owned key (`shpyrd-platform`, owner on every bucket, never stored); usage from
  `GetBucketInfo`, capacity from the node's data partition; finalizer for cleanup.
- RBAC: the server's ClusterRole already spans `shpyrd.io`; the project viewer role reads
  `objectbuckets`. Cluster page card and `GET /api/cluster/object-storage` need
  cluster.admin.
- Verified on OKE: a project's key writes and lists its own bucket, is refused on the
  platform's bucket and sees only its own in `ls`; deleting the resource removes key,
  objects and bucket.
