# RFC-0046 Object storage extension

**Status:** in progress

**Owner:** unassigned

**Depends on:** RFC-0002 (implemented), RFC-0059 (platform CA), RFC-0060 (storage classes)

**Creation date:** 2026-09-22

**Last update:** 2026-09-25 (design settled: MinIO on every profile, scoped credentials per consumer, provider storage as the offsite tier)

## Summary

An `object-storage` extension giving the platform an S3-compatible bucket store with a
credential per consumer: MinIO in the cluster on every profile, TLS from the platform CA,
buckets declared as `ObjectBucket` resources by the extensions that need them (Postgres
backups, platform backups, Loki). The provider's object storage (S3, OCI Object Storage)
is the offsite tier: where data must survive the cluster, RFC-0037 writes there directly,
and MinIO replication to it is the follow-up.

## Motivation

Three RFCs need durable object storage; each configuring its own would triple the work
and the credentials.

### Goals

- `shpyrd extensions enable object-storage` and consumers get a bucket and a credential
  that opens only that bucket.
- The same client model on kind, OKE and EKS; nothing in a project namespace can reach
  another project's data.

### Non-Goals

- Exposing buckets to applications as a resource (a later resource type).
- Replacing the provider's object storage for archives; MinIO here is the platform's
  working store, on the profile's block storage class.

## Proposal

- **One store, every profile.** MinIO (single node, pinned chart) in `shpyrd-system` on a
  volume of the profile's class (`SHPYRD_OBJECT_STORAGE_SIZE`: 20Gi local and AWS, 50Gi on
  OCI, the block volume minimum), served with TLS from the platform CA
  (`object-storage.shpyrd-system.svc:9000`), root credential generated by a hook into
  Secret `object-storage-root` that only the platform reads.
- **`ObjectBucket`** (`shpyrd.io/v1alpha1`, namespaced): a consumer declares
  `spec: {retentionDays?, versioning?}` in its namespace; the extension's controller creates
  the bucket `shpyrd-<namespace>-<name>`, a MinIO user whose policy opens that bucket and
  nothing else, and writes Secret `<name>-object-storage` next to it (`AWS_ACCESS_KEY_ID`,
  `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL`, `BUCKET`, `AWS_REGION`, plus `accessKeyId` /
  `secretAccessKey` for consumers that name keys, such as CloudNativePG). Status carries
  the endpoint, bucket, usage and phase. Deleting the resource deletes the user and,
  with `spec.deletionPolicy: Delete` (the default), the bucket.
- **Cluster page and CLI.** An Object storage card (capacity of the volume, buckets with
  size and object count) and `shpyrd object-storage buckets`.
- **Why not the provider's service as the store?** S3 or OCI Object Storage can only hand
  out credentials scoped per consumer through cloud IAM (one IAM user or Pod Identity
  association per project, created by the platform with cloud SDKs and IAM rights). Until
  that exists, a shared provider key in project namespaces would open every project's
  backups to any project member who can exec into a database pod. MinIO scopes users
  natively, so the isolation holds on day one on every profile.
- **The offsite tier.** RFC-0037 (platform backups) writes to the provider's bucket
  directly with its own credential, from the platform namespace only, because its purpose
  is to survive the cluster. MinIO bucket replication to that bucket (one credential, held
  by MinIO) is the natural next step for the other consumers and is tracked as a
  follow-up.

### Alternatives

- **The provider's object storage as the store** (the first draft's goal). Deferred for
  the credential reason above; the data path is one flag away once per-consumer cloud
  credentials exist.
- **A bucket per cluster with prefixes per consumer.** Same credential problem, harder
  usage accounting.
- **SeaweedFS, Garage.** Lighter, but no per-user policies in the S3 dialect the consumers
  speak; MinIO's admin API does users, policies, lifecycle and usage.

## Design Details

- Chart `minio/minio` 5.4.0 (MinIO RELEASE.2024-12-18), `mode: standalone`, `replicas: 1`,
  `existingSecret: object-storage-root`, `tls` from Secret `object-storage-tls`
  (Certificate on the `shpyrd-ca` ClusterIssuer, applied by the hook), console disabled,
  requests 256Mi, limit 1Gi.
- Hook `object-storage-credentials`: the root Secret (kept when present) and the
  Certificate.
- Controller: `minio-go` for buckets, lifecycle and versioning; `madmin-go` for users,
  policies and data usage; the server trusts the platform CA already (`SSL_CERT_FILE`).
  Access keys are 20 random alphanumerics, secrets 40; the policy is
  `s3:*` on `arn:aws:s3:::<bucket>` and `arn:aws:s3:::<bucket>/*`.
- RBAC: the server's ClusterRole gains `objectbuckets`; the project viewer role reads them.
- Usage is refreshed on reconcile and every 10 minutes; the cluster API summarises it.
